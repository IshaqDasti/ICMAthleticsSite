# Database Changes (Prisma + Supabase Postgres)

## Workflow: db:push, not migrations

- Schema lives in `prisma/schema.prisma`. There is **no `prisma/migrations/` directory** — this project has never used migration files.
- Apply schema changes with `npm run db:push` (= `dotenv -e .env.local -- prisma db push`). All `db:*` scripts load `.env.local` via dotenv; plain `npx prisma …` won't see the env vars.
- `npm run db:migrate` exists (`prisma migrate deploy`) but is a trap: with no migrations directory it deploys nothing. Don't introduce `migrate dev` casually — it would want to reset/baseline the live Supabase DB.
- The Prisma client is regenerated by `npm run build` (`prisma generate && next build`); in dev, run `npx prisma generate` (or restart `npm run dev` after a build) so TypeScript sees new fields.
- `npm run db:studio` opens Prisma Studio for direct inspection.

## Connection strings

- `DATABASE_URL` = Supabase **transaction pooler** (PgBouncer, port 6543) — runtime queries.
- `DIRECT_URL` = direct connection (port 5432) — declared as `directUrl` in the datasource; Prisma automatically uses it for schema operations (`db push`, introspection). Never point `db:push` at the pooler.
- Details and setup: `DEPLOYMENT.md` at repo root.

## Naming: tables snake_case, columns camelCase

`@@map` renames **tables only** (`games`, `player_game_stats`, …); columns keep their Prisma names (`homeScore`, `gameId`, `playerId`). Consequences:
- Raw SQL must double-quote camelCase identifiers: `s."gamePlayed"`, `"playerId"` (see `recalculatePlayerCareerStats` in `src/lib/db/mutations/standings.ts` and the boxscore route).
- Supabase Realtime payload keys and filter columns are the **camelCase** names. Existing snake_case usages (`payload.new.home_score` in `ScorekeeperBoard`, `game_id=eq.` filter in `BoxScoreView`) do not match real columns — don't copy them into new code. See [live-scoring].

## Checklist: adding a table or column

1. Edit `prisma/schema.prisma` (defaults on new columns so existing rows are valid; `db push` on a non-nullable column without default will prompt/fail).
2. `npm run db:push`.
3. Regenerate the client: `npx prisma generate` (build does it automatically on deploy).
4. **If public pages must live-update from the new table**: only tables in the `supabase_realtime` publication broadcast. Run in the Supabase SQL editor: `ALTER PUBLICATION supabase_realtime ADD TABLE <table_name>;` Current whitelist (per `DEPLOYMENT.md`): `games`, `player_game_stats`, `team_game_stats`, `team_seasons`, `announcements`. Forgetting this is the classic "realtime silently does nothing" failure.
5. **Seed impact**: does `prisma/seed.ts` need to populate it? (See below.)
6. **Derived-data impact**: if the column feeds scores/stats, update `applyGameEvent`/`undoGameEvent` (`src/lib/db/mutations/stats.ts`), `finalizeGame`/`unfinalizeGame`/`recalculateTeams`/`recalculatePlayerCareerStats` (`src/lib/db/mutations/standings.ts`), and the raw-SQL boxscore route (`src/app/api/games/[id]/boxscore/route.ts`). See [stats-and-standings].
7. Verify: `npx tsc --noEmit` and `npm run build` (no tests exist).

## Cascade behavior — deletion blast radius

`onDelete: Cascade` is declared on: `TeamSeason.team`, `TeamSeason.season`, `PlayerCareerStats.player`, `PlayerGameStats.game`, `PlayerGameStats.player`, `TeamGameStats.game`, `TeamGameStats.team`, `GameEvent.game`. Relations without an explicit action get Prisma defaults: optional → SetNull, required → Restrict.

- **Delete a Game** → cascades its `GameEvent`, `PlayerGameStats`, `TeamGameStats`. Does **not** touch `TeamSeason` or `PlayerCareerStats` — deleting a COMPLETED game requires running both recalcs afterward ([stats-and-standings] runbook).
- **Delete a Player** → cascades their `PlayerCareerStats` and all their `PlayerGameStats` (rewriting box-score history). `GameEvent.playerId` is a **plain string with no FK** — events keep orphaned ids. `Player.team` is optional, so team deletion just nulls `teamId`.
- **Delete a Team** → cascades `TeamSeason` (standings rows) and `TeamGameStats`; sets players' `teamId` to null; **blocked (Restrict)** if the team has any `Game` as home or away — reassign or delete games first.
- **Delete a Season** → cascades `TeamSeason`; **blocked** while any `Game` references it (`Game.season` required, no cascade). `Announcement.season` is optional → SetNull.
- `User.managedTeam` optional → SetNull.

## Enums

`UserRole`, `SeasonStatus`, `GameStatus`, `GameType`, `EventType` — all real Postgres enums; adding a value requires a schema edit + `db:push`.

Adding an `EventType` value is never just the enum. Downstream, all must change together:
- `applyGameEvent` — the `isPoint/isRebound/…` flags decide which of the four transactional writes fire; a new type with no flag writes an event row and nothing else. Also note it throws unless `playerId` or `substituteStatsId` is present (team-only events unsupported today).
- `undoGameEvent` — mirror compensating decrements.
- `ScorekeeperBoard` (`src/components/live/ScorekeeperBoard.tsx`) — its local `type EventType` union is only the four live types; add the button, optimistic update, failure rollback, undo handling, and activity-log label/badge.
- Box score surfaces if the stat should display (`src/components/boxscore/`), plus career/standings recalcs if it aggregates.
- Existing dead values `QUARTER_END`, `GAME_START`, `GAME_END`: in the enum, never emitted. Precedent: don't add enum values speculatively.
- Postgres refuses to drop enum values via `db push` without data loss acceptance — treat enum additions as one-way.

## Seed script (prisma/seed.ts)

`npm run db:seed` runs it with tsx + `.env.local`. What it does:
- Upserts season `summer-2026`, the 10 teams, and their `TeamSeason` rows — **idempotent**.
- Imports players from the CSV at repo root: `2026 mens summer league final roster.csv` (header names like "Attendee First Name", "Team Name Spring 26", "Name on Jersey"). If the file is missing, it logs a warning ("Roster CSV not found…") and skips players; season/teams/games still seed. Slug collisions get `-1`, `-2` suffixes.
- Creates the Summer 2026 schedule (games hardcoded in the file); TBD playoff/all-star games are skipped, to be created later in admin.
- **NOT idempotent for players and games**: both use `create`, so re-running the seed duplicates every player (with suffixed slugs) and every game. Never re-run against a database that already has them; seed is for fresh databases only.
- New required fields on `Player`/`Game`/`Team` must be added here or the seed breaks fresh-environment setup.

## Gotchas

- `db push` prints a diff and can DROP columns/tables you removed — read the preview; there are no migration files to recover from, only Supabase backups.
- PgBouncer transaction pooling (port 6543): session-level Postgres features (LISTEN, session GUCs, advisory locks held across statements) won't work through `DATABASE_URL`. Prisma's standard queries and `$transaction` are fine.
- Uniques with nullable columns: `@@unique([gameId, playerId])` on `PlayerGameStats` permits unlimited `playerId = null` rows per game — that's how walk-on substitutes work. Don't "fix" it.
- `GameEvent.playerId` / `substituteStatsId` / `teamId` / `createdBy` are intentionally FK-less strings — the event log survives entity deletion but can hold orphaned ids; never join it with an inner join that assumes integrity.
- After `db:push` in dev, stale generated client = runtime `Unknown arg` errors; regenerate/restart before debugging further.
